## G-05-1 — x86_64 CI failure: missing /bin/rc breaks #!/bin/rc rc-script exec from mk recipes (membername → boot(8) link)
- **Date:** 2026-11-03
- **Error patterns:** `membername: No such file or directory`, `SUBSET-BUILD-FAIL: boot(8) aarch64 build`, `main: undefined: boot`, `semacquire: configembed: not defined`, `cannot execute: required file not found`, "works on the dev VM, fails on fresh CI host", reported-symptom-vs-raw-log mismatch
- **Root cause(s):** `rc/bin/membername` (shebang `#!/bin/rc`, invoked from `sys/src/9k/boot/mkfile.aarch64:50` and both shared bootmkfile templates) needs the kernel to exec `/bin/rc`; the mount namespace (build/aarch64/nsrun.sh) shares the distro `/bin` and never provided `/bin/rc`. Passing legs were masked by an undocumented manually-placed `/bin/rc` in the long-lived lima VM; the legacy docker path codified it (build/Dockerfile:42) but the nix/namespace path never did. The "arch-specific" axis was correlation, not cause.
- **Fix:** nsrun.sh root section binds `$PLAN9/bin/rc` over `/bin/rc` inside the private mount namespace (touch mountpoint if missing; fail-hard if `$PLAN9/bin/rc` absent). Commit d758c2071 `fix(05): G-05-1 ...`.
- **Files changed:** build/aarch64/nsrun.sh
- **Why not caught:** no gate exercised the namespace build on a truly fresh host before the first x86_64 CI run — both proven legs shared one VM image carrying manual state; the env contract ("/bin/rc must exist") was implicit.
- **Recurrence guard:** the nsrun.sh bind itself (fresh hosts now get /bin/rc deterministically); plus the debug-verified repro recipe (emulated x86_64 docker: ubuntu:24.04 + nix `sandbox=false` + `nix run .#boot-r9-smoke`) is recorded in .planning/debug/DEBUG-G-05-1.md for future arch-leg bring-up.
- **Meta-lesson:** when a report says "log ends at X with zero output and no failure marker," fetch the RAW CI log before theorizing — streaming/partial views mislead; here the raw log showed the true failure two stages later with its marker intact.

## x64-kzero-panic-after-dealloc-fix — x86_64 r9 exec reuses freed page tables once frees became real (KZERO panic / #UD)
- **Date:** 2026-11-19
- **Error patterns:** `panicked at x86_64/src/proc.rs:361:5`, `PA 0x... outside the KZERO window`, `user trap: unhandled vector 6 pc=0x204ff8`, `process N exited: "sys: trap"`, panic right after `init: starting /bin/rc`, x86_64-only (aarch64 green on the same r9), started at an allocator fix that made frees real (r9 8958c9e), invalid opcode at a 0xff8 page offset, garbage PA whose bytes decode as amd64 code
- **Root cause(s):** r9 `x86_64/src/proc.rs` `Proc::free_user_mappings` freed the user-half intermediate page tables (`mapping_tables`: PDPT/PD/PT) while the proc's PML4 still linked them (PML4[0] text/data, PML4[255] stack); EXEC keeps that PML4 and maps the new image through it, so the walk descended into freed pages that `alloc_phys_page` was handing out again as the new image's leaves — text bytes walked as PTEs (KZERO panic) and stale stack-path walks wrote PTEs into text (slot 511 = offset 0xff8 → #UD); AND r9 8958c9e made `bitmapalloc` deallocate really free (correct), which turned the previously leaked-and-intact tables into reused pages. aarch64 never frees intermediate tables, hence green.
- **Fix:** r9 cec2299 `fix(x86_64): unlink the user-half tables before freeing them` — new `unlink_user_half()` clears PML4[0..256) and reloads CR3 when that root is active, called in `free_user_mappings` BEFORE the table frees; compile-time assert that the kstack slot (400) is outside the cleared range; allocator untouched. Harvey pinned at b0e3cef8f.
- **Files changed:** r9 x86_64/src/proc.rs
- **Why not caught:** no gate existed for this class — every free leaked before 8958c9e, so free-while-linked was invisible; the x86_64 host tests never re-mapped through a root after `free_user_mappings`; the composed x64 gates were the first to run on the fixed allocator (8958c9e's own verification covered the port suite and aarch64, and flagged the x86_64 kernel bytes as changed but did not run the x64 composed gates).
- **Recurrence guard:** regression test `x86_64/src/proc.rs:proc::tests::free_user_mappings_unlinks_the_freed_tables_for_exec_reuse` (PML4 user half empty after free; every reachable table owned after re-map; kills the unlink-removed / 0..255 / 1..256 mutants) + the `KSTACK_PML4_INDEX >= USER_PML4_SLOTS` const assert. Note: run x86_64 host tests explicitly (`cargo test -p x86_64 --bins --target x86_64-unknown-linux-gnu`) — `cargo xtask test` inside `nix develop` skips the arch leg (no rustup).
- **Meta-lesson:** an allocator fix that makes frees real is a cross-arch event — re-run every arch's composed gates, and audit each "free" for the free-while-still-linked shape (unlink → flush → free). Repro recipe for x86_64 CI on an Apple-silicon Mac: Docker Desktop amd64 (Rosetta) ubuntu:24.04 `--privileged`, single-user nix with `sandbox = false` + `filter-syscalls = false`, a non-root builder with passwordless sudo, and **gcc installed** (ubuntu-latest parity — mkimage's authdomain-gen needs a host cc).

## shared-fgrp-pipe-leak — aarch64 r9: a fd table shared through plain rfork(RFPROC) is never drained at its last sharer's exit (backquote reader hangs)
- **Date:** 2026-11-19
- **Error patterns:** rc backquote hangs forever, `x=`{/bin/rfdprobe -s}` never returns, all procs exited but reader never sees EOF, pipe write end leaks, shared fd table, rfork(RFPROC) without RFFDG/RFCFDG, libthread proccreate exposure, fork() control passes, no-pipe control passes, HVF and TCG identical, aarch64-only (x86_64 fine), strong_count 2 at the last sharer's exit
- **Root cause(s):** r9 aarch64/src/syscall.rs `exit_tail` is `-> !` (park_forever / sched_from_moribund) and held the detached fd-group Arc as a LOCAL, which is never dropped; every non-last sharer's exit leaked one strong ref, so the last sharer read strong_count 2, skipped drain_all, and the pipe writer in the table was never close_chan'd. x86_64 had the explicit `drop(detached)` since c4f2f2c (#44, framed as a heap leak) — never ported to aarch64.
- **Fix:** r9 3a1c9e5 `fix(aarch64): release the exiting proc's fd-group reference before exit_tail diverges` — the sweep moved into a RETURNING helper `proc::release_fd_group` so the reference drops at its return; drain/close semantics unchanged.
- **Files changed:** r9 aarch64/src/proc.rs, r9 aarch64/src/syscall.rs
- **Why not caught:** no gate existed for this class — the sweeps use fork()'s RFFDG copies only; the x86_64 #44 churn gate found the same leak as heap growth and its fix was not mirrored to aarch64; exit_tail diverges, so no host test reached it.
- **Recurrence guard:** host tests `aarch64/src/proc.rs:proc::fdgrp_release_tests` (3 tests, real devpipe pipes; kill the forget(detached) mutant) + the returning-helper structure; boot-level reproducer `x=`{/bin/rfdprobe -s}; echo DIAGS $x` (Harvey build/aarch64/rfdprobe.c) must print `DIAGS rfdprobe: share ok`.
- **Meta-lesson:** in a diverging (`-> !`) kernel tail, Rust never drops locals — an Arc/Chan/Vec held there leaks silently, and a refcount-gated cleanup (strong_count == 1) then never fires for anyone else. Audit every owning value in diverging frames; when one arch fixes such a leak, check the sibling arch the same day. Venue note: run boot gates from a scratch Harvey clone (`HARVEY` = clone root) when a plan executor owns the main checkout; `HARVEY_GUEST_DIR` keeps lima builds apart.

## create-ocexec-not-marked — r9 create(.., OCEXEC) left the new chan unmarked, so the fd survived exec (both arches)
- **Date:** 2026-11-20
- **Error patterns:** fd survives exec, close-on-exec ignored on create, `cexecprobe: LEAK create fd=3`, OCEXEC stripped, create vs open asymmetry, new-file arm only (existing-file re-create is fine), silent fd leak, /srv post fd inherited by exec'd children, lib9p postfd, HVF and TCG identical, both arches
- **Root cause(s):** r9 `sys_create`'s new-file arm (aarch64/src/syscall.rs, x86_64/src/syscall.rs) passed `mode & !(OEXCL|OCEXEC)` to `create_chan_union` (correct — the device never sees either bit) but never set `cexec` on the created chan afterwards (the donor chan.c Acreate's `cnew->flag |= CCEXEC`), so exec's `take_cexec` sweep kept the fd. The existing-file arm opens through `namec::open_chan`, which records the bit.
- **Fix:** r9 437b752 `fix: create(OCEXEC) marks the new chan close-on-exec on both arches` — `create_new_chan` in both arches' syscall.rs owns the strip AND the mark; 42203d8 re-wires the boot-iso FOD hash (x86_64 kernel bytes changed). Arch code only.
- **Files changed:** r9 aarch64/src/syscall.rs, x86_64/src/syscall.rs, x86_64/src/exec.rs (close_on_exec_fds pub(crate) for a test), flake.nix (hash); Harvey build/aarch64/cexecprobe.c (`-c` create leg)
- **Why not caught:** no gate existed for this class — 20-10's cexecprobe pinned only the open arm, the tier-1 creates are plain, port's namec test covers open_chan only, and sys_create had no host test on either arch.
- **Recurrence guard:** host tests `aarch64/src/syscall.rs:create_cexec_tests::*` (2) and `x86_64/src/syscall.rs:tests::{created_ocexec_fd_is_taken_by_the_exec_sweep, create_records_ocexec_beside_the_other_create_bits, create_syscall_ocexec_fd_is_closed_by_exec}` (kill the mark-removed mutant; the x86_64 MockStack dispatch test also kills a helper bypass); boot reproducer `cexecprobe -c` must print `cexecprobe: create ok` (plan 20-11: `T1-OK cexeccreate`).
- **Meta-lesson:** an fd-state bit carried in the mode word (OCEXEC, ORCLOSE) must be recorded on EVERY arm that yields a chan — open, create-new, create-existing; when one arm learns a flag, grep the siblings the same day. Method notes: darwin host `7c -FTVw -I$H/arm64/include -I$H/sys/include` + `7l -l -E _main -o x x.7 $H/arm64/lib/libc.a` builds arm64 probes whose text+data are byte-identical to the guest build (no lima venue needed); bake a probe image from a scratch Harvey clone with the executor's userland copied (diff -r) and only the probe swapped; a probe that needs fresh writable names can `rfork(RFCENVG)` and create in its private /env (r9 aarch64 has no remove); in the amd64 container use `docker exec -u builder -e HOME=/home/builder` or nix is not on PATH.

## orclose-local-devices — r9 ORCLOSE had no effect on local devices: /srv and /env files outlived their last close (both arches)
- **Date:** 2026-11-20
- **Error patterns:** stale /srv post after the server exits, remove-on-close ignored, ORCLOSE no effect, `rcloseprobe: LEAK srv|dup|exit|env|env-open`, lib9p postfd OWRITE|ORCLOSE|OCEXEC, devsrv/devenv no remove, CRCLOSE missing, mounted (devmnt) files fine, HVF and TCG identical, both arches
- **Root cause(s):** AND-gate, both in port/src: (1) nothing recorded ORCLOSE on a chan (no CRCLOSE twin on `Chan`); (2) devsrv and devenv had no remove op (private registry and EnvGroup), and the only remove routing was x86_64-local (devcap only). devmnt was already right (ORCLOSE rides the Topen/Tcreate mode byte; the server removes at clunk).
- **Fix:** r9 5629cf0 — `Chan.rclose: Option<Arc<()>>` (shared by dup/op_clone = the open's refcount); `namec::mark_fd_state` (OCEXEC + ORCLOSE, used by open_chan and both arches' create_new_chan); `namec::remove_chan`, the ONE device-remove dispatch (cap/srv/env) shared by REMOVE and the close path; `remove_if_last_rclose` from close_chan and drop_op_ref (srv/env only — the donor's capclose ignores CRCLOSE); devsrv/devenv remove ops; x86_64 remove_chan routes through port's. fa38402 re-wires the boot-iso hash. Owner-approved port/src scope (option C); aarch64 REMOVE(25) left to plan 20-14.
- **Files changed:** r9 port/src/{dat,namec,devsrv,devenv,namec_tests}.rs, aarch64/src/syscall.rs, x86_64/src/syscall.rs, flake.nix; Harvey build/aarch64/rcloseprobe.c, subset-build.sh, mkimage.sh
- **Why not caught:** no gate existed for this class — no sweep entry opens or creates ORCLOSE, its live callers (lib9p servers, rio, plumber) are not in the arm64 sweep, a leaked /srv or /env name fails nothing, and devsrv/devenv had no remove to test.
- **Recurrence guard:** host tests `port/src/namec_tests.rs:orclose_*` (3; kill close-arm-removed / last-close-guard-removed / mark-not-recorded), `{aarch64,x86_64}/src/syscall.rs:…created_orclose_srv_post_goes_at_the_last_close`, x86_64 `remove_round_trips_through_the_devcap_arm_and_refuses_unported` (srv arm); boot reproducer `rcloseprobe` must print `rcloseprobe: ok` (plan 20-11: `T1-OK rcloseprobe`).
- **Meta-lesson:** an fd-state bit needs BOTH halves — the record on every arm that yields a chan AND the device op it triggers; check the device half exists before calling the flag "unported". Last-close semantics on r9's by-value `Chan` ride a shared `Arc` (devmnt's fid pattern), and they work only because every drain consumes chans one at a time (`drained.drain(..)`) — a borrowed drain loop would never see the last reference. Open risk: fdgrp `op_done` releases op-refs under the fd-group lock, so a raced ORCLOSE remove runs under it (commented in namec.rs/dat.rs). Harvey hazard: adding a probe to mkimage.sh makes `R9_SKIP_BUILD=1` bakes over an older userland fail until one rebuild.

## fork-child-pc-align-fault — aarch64 r9 fork child ran the previous process's STALE INSTRUCTIONS: rfork copied text through a data alias with no I-cache maintenance (WINDOWS #49 residual)
- **Date:** 2026-11-21
- **Error patterns:** `user trap: unhandled ec=0x22` (PC alignment) at an odd rc DATA address (0x318e7 = Builtin "rfork" name), `rc: can't dup 199533 to 202983` (values > 16 bits from short fields = stale stack args), `user fault: unresolvable ... addr=0x1` in strncmp via searchpath, backquote child forks cat instead of exec'ing it, always the same fork (pid 49, `conv=`{cat /net/ipifc/clone}` right after `echo` + `bind` exit), HVF-only (0 TCG), ~0.2–0.5%/boot, memory + translations verified consistent at every checkpoint, first seen after 8958c9e (real frees)
- **Root cause(s):** r9 aarch64/src/proc.rs `rfork_copy` wrote every child text page into a fresh physical page through the KZERO DATA alias with no I-cache maintenance ("identical bytes at identical VAs" — wrong: the PA is new); CTR_EL0.DIC = 0 and the HVF host's (Apple M-series, 4K granule) instruction side keeps stale code per (VA, PA) across unmap+tlbi+remap — so when the child's copy of VA v lands on the page the previous process executed at the same v, the child runs the old owner's instructions; contributing: 8958c9e made frees real and the next-fit allocator recycles a just-exited command's pages into the next fork (deterministic layout put rc's simple.c page 0x18000 on bind's just-executed page 0x18000)
- **Fix:** r9 79c55b1 (dc cvau per copied text page + ic ialluis; dsb ish; isb once per fork that copied text) and 46a5c87 (TextCopy = the single rfork copy path owning that maintenance; boot-time selftest); local, unpushed at archive time
- **Files changed:** r9 aarch64/src/proc.rs, aarch64/src/vm.rs, aarch64/src/textcopy.rs (new), aarch64/src/main.rs
- **Why not caught:** no gate existed for this class — TCG and host tests cannot observe an I-cache; on HVF it was a rare residual indistinguishable from the old #49 TLB defect; forkstress checks data, not code; the 20-02 I-cache experiment was "ruled out" while pages were never reused and not revisited when reuse began
- **Recurrence guard:** r9 46a5c87 `aarch64/src/textcopy.rs` `selftest()` from main9 on every exec-profile boot — prints `icache: rfork text-copy selftest N/64 fresh (control without maintenance: M/64 stale)` and panics unless 64/64 (HVF: the maintenance-removed mutant gives 0/64 and fails every gate boot; control 64/64 stale proves the venue is sensitive; TCG control 0/64 = blind venue); host test `textcopy::tests::text_copies_owe_exactly_one_icache_sync`
- **Meta-lesson:** when memory and translations check out but a process behaves as if it skipped its own stores, suspect the INSTRUCTION side: read CTR_EL0 (DIC/IDC/L1Ip), and find every path that writes code through a data mapping. A cheap boot-time self-test (data-alias rewrite of a warmed code page, fetch at the same VA, with and without IC maintenance) decides the hardware question deterministically in one boot, where rate statistics needed thousands. Re-test any "ruled out" cache-maintenance hypothesis when page lifetime changes (frees becoming real). Method: a text-PA reuse tracker (last text owner + VA + hash per PA) shows which fork lands code on a just-executed page at the same VA — the deterministic precondition behind a "fixed-site" Heisenbug. Venue: parallel HVF series from scratch Harvey clones (net-smoke has no hostfwd, -smp 1); the darwin host 7c/7l have a 4 MiB sbrk arena (WINDOWS #30) that caps probe size.
